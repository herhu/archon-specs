npx archonspecs init

Universal Integration (MCP)

Register Archon Specs as a Model Context Protocol (MCP) server in your favorite IDE.

A. Copy Configuration

{
  "mcpServers": {
    "archon": {
      "command": "npx",
      "args": [
        "-y",
        "archonspecs",
        "mcp"
      ]
    }
  }
}

B. Load into environment

  • Claude Desktop (macOS):
    ~/Library/Application Support/Claude/claude_desktop_config.json
  • Antigravity IDE:
    ~/.gemini/antigravity/mcp_config.json
  • Claude Desktop (Windows):
    %APPDATA%\Claude\claude_desktop_config.json
  • Cursor / VS Code:
    Add as New MCP Server (SSE) in Settings
⚡ That's it

No config files, no boilerplate, no YAML. Your agent now has access to the full Archon governance engine via MCP. Start with the sharding process to understand how to structure your first project.

System Design

Governed Architecture

Archon is built on a three-layer governed architecture that ensures every line of code generated is traceable, compliant, and architecturally sound.

The Conceptual Shift

In traditional AI coding, the LLM carries the architecture in its context window. In Archon, the Control Plane carries the architecture, and the LLM carries only the intent. State is internal and canonical.

The Mental Model

Archon converges the best practices of modern infrastructure and build systems into a single architectural platform:

Kubernetes Desired State + Reconciliation
Terraform Plan/Apply Lifecycle + Drift
Bazel Deterministic Build Graphs
Git Lineage + Immutable History
LSP Semantic Code Mutation Layer

The Materialized Stack

Archon doesn't just generate boilerplate; it materializes a production-grade NestJS Enterprise Ecosystem. Every project comes pre-configured with a battle-tested technical stack:

Core: NestJS 10+

Docs: Swagger / OpenAPI
Validation: Class Validator

  • Worker Pool: A pool of specialized MCP workers that execute heavy-duty compilation and validation tasks in isolation.

The Archon CLI (`archonspecs`) is a high-performance bridge that connects your local development environment to the Archon Governance remote. It handles secure tool proxying, local shard management, and real-time file-system mutations.

Install the Archon CLI globally via npm to use it across all your projects.

npm

npx archonspecs -token <YOUR_SECRET_TOKEN>

The Sharding Process

Large-scale systems are too complex to manage as a single file. Archon solves this through Domain Sharding.

Each module of your system is developed as an independent shard—a discrete piece of the architectural puzzle. Our compilation engine then takes these shards and merges them into a unified DesignSpec.json, validating every relationship and constraint along the way.

graph TD S1[Identity Shard] --> MCP[MCP Validation & Compilation] S2[Billing Shard] --> MCP S3[Inventory Shard] --> MCP MCP --> DS[Final DesignSpec.json] style S1 fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style S2 fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style S3 fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style MCP fill:#ff5d01,stroke:#fff,stroke-width:2px,color:#fff style DS fill:#2d2d2d,stroke:#ff5d01,stroke-width:2px

This process ensures that your "Identity Management" shard never conflicts with your "Billing" logic, maintaining perfect isolation and integrity.

🧩 Why Sharding?

Sharding allows multiple agents (or humans) to work on different parts of the system simultaneously without merge conflicts. More importantly:

  • Token Optimization: We only send the relevant shard to the LLM, drastically reducing context window usage and costs.
  • Safe Scaling: Add new domains without risking the integrity of existing modules.
  • Enhanced Security: Shards provide natural boundaries for permissioning and auditing.

Generation Capabilities

Archon's compilation engine ships with a library of over 180 specialized generation functions organized across 20 categories. Rather than loading everything unconditionally, the engine is demand-driven: the agent inspects the available catalog, selects only the modules the spec actually requires, and declares them in the Architecture Contract. The engine then loads exclusively those modules at compile time.

🧠 Why This Matters

Each project gets a compilation context shaped to its requirements — not a generic runtime with everything turned on. A financial system that needs precise decimal arithmetic gets math. A localized platform gets i18n and inflection. The agent decides; the engine enforces.

The Flow

graph LR A[archon_list_modules] --> B[Agent Analysis] B --> C[archon_create_architecture_contract] C --> D[DesignSpec.json] D --> E[Engine loads selected modules] E --> F[Compilation] style A fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style B fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style C fill:#ff5d01,stroke:#fff,stroke-width:2px,color:#fff style D fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style E fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style F fill:#2d2d2d,stroke:#ff5d01,stroke-width:2px
  1. Agent calls archon_list_modules — receives the full catalog with descriptions for each function.
  2. Agent reads the spec requirements and determines which categories are needed.
  3. Agent calls archon_create_architecture_contract with the selected list.
  4. Shard compiler merges the selection into DesignSpec.json.
  5. Engine loads only those modules during compilation — nothing else.

Declaring in the Architecture Contract

When the agent creates the Architecture Contract, it includes the selected categories:

archon_create_architecture_contract 
{
  "version": "1.0.0",
  "domainShards": ["billing", "inventory", "identity"],
  "handlebarsHelpers": ["math", "date", "inflection", "array"],
  "platform": { "terraform": true },
  "modules": [{ "type": "queue.bullmq", "name": "jobs" }]
}
📋 Agent Guidance

Use archon_list_modules before authoring the Architecture Contract. Each entry in the catalog includes the function name, category, and a usage description — everything needed to make an informed selection. Only declare what the spec's domains genuinely require. Over-declaring adds no functionality and signals a shallow analysis.

Incremental Compiler

Codebases should evolve, not rot. The Incremental Compiler is designed for the long-term health of your project. Unlike traditional generators that overwrite your work, our compiler is region-aware—preserving your manual customizations (marked with // @archon-manual) while updating the governed structural code around them.

🚀 The V2 Evolution
One of the biggest upgrades in ArchonSpecs V2 is the move from a monolithic compiler to an incremental distributed architecture compiler.

From O(N) to O(C)

In legacy systems, every small change triggered a "recompile the universe" event. At enterprise scale (100+ domains, 2,000+ entities), this monolithic approach collapses. Archon V2 recompiles only what changed and its immediate affected dependencies.

V1: Monolithic
O(N) ➔ All Specs
  ➔ Full Parse
  ➔ Full Validate
  ➔ Full Compile
V2: Incremental
O(C) ➔ Changed Shards
  ➔ Affected Deps
  ➔ Cached Partials
  ➔ Parallel Merge

1. Architecture Sharding

Instead of a single DesignSpec.json, the architecture is split into independent compilation units (Shards) stored in spec/domains/.

2. Deterministic Fingerprinting

Every shard is normalized and hashed before compilation. The compiler uses these fingerprints to instantly detect if a shard needs processing without parsing the entire tree.

3. DAG-Based Dependency Resolution

Shards declare their dependencies explicitly. Archon builds a Directed Acyclic Graph (DAG) to guarantee a deterministic compilation order and detect circular dependencies.

graph TD Identity --> Billing Billing --> Invoices Identity --> Notifications style Identity fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style Billing fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style Invoices fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style Notifications fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px

4. Transitive Invalidation

If the Identity shard changes, Archon automatically invalidates downstream shards (Billing, Invoices). This ensures that architectural changes propagate safely and the final system remains consistent.

Parallel Compilation

Because shards are isolated, non-dependent branches (like Notifications and Analytics) compile simultaneously, drastically reducing latency for large swarms.

Validation Gates

Before entering the DAG, every shard passes through a strict validation gate that checks schema correctness, naming rules, and architectural invariants.

Engineering Memory

Engineering Memory is Archon's RAG-powered semantic knowledge layer — a curated library of thousands of real-world architecture diagrams, patterns, and system blueprints. When the requirement analysis agent begins working on your spec, it uses Retrieval-Augmented Generation (RAG) to query this library and retrieve the most relevant context instantly, without scanning the open web or wasting tokens on broad research.

🔒 Pro Feature

Engineering Memory is available on the Pro plan and is managed entirely by Archon through your account. No setup required — it's always on when you're on Pro.

What It Contains

The library is built and maintained by Archon. It includes:

🗺️

Architecture Diagrams

Thousands of real system diagrams — microservices, event-driven, hexagonal, CQRS, monorepos — indexed semantically so the agent can find structural analogues to your system.

📐

Engineering Patterns

Proven patterns across domains: auth flows, data access layers, job queue architectures, API gateway contracts. Ready to inform your spec without manual research.

⚖️

Decision Records

Curated architectural decision records from high-quality open-source systems. The agent can retrieve why specific tradeoffs were made in systems structurally similar to yours.

How It Helps the Agent

When you kick off a new project, the requirement analysis agent automatically queries Engineering Memory before drafting your DesignSpec. Instead of reasoning cold, it retrieves the most structurally relevant diagrams and patterns — scoped to your domain — and uses them as context.

graph LR A[Your Requirements] --> B[Requirement Analysis Agent] B --> C[Query Engineering Memory] C --> D[Relevant Diagrams & Patterns] D --> B B --> E[DesignSpec Draft] style C fill:#ff5d01,stroke:#fff,stroke-width:2px,color:#fff style D fill:#1a1a1a,stroke:#ff5d01,stroke-width:2px style E fill:#2d2d2d,stroke:#ff5d01,stroke-width:2px

The result: faster spec drafting, fewer hallucinations, lower token usage — because the agent grounds its output in real reference material rather than generating from scratch.

Privacy & Ownership

✅ We do not ingest your project

Engineering Memory is a read-only curated library. Archon never scans, indexes, or stores your codebase, specs, or architecture documents. Your project remains entirely yours — on your machine, under your control.

Coming Soon — Private Project Memory

A future release will allow you to opt in to ingesting your own project into a private, isolated memory space. This would give the agent access to your team's actual decisions, patterns, and architecture history — making it dramatically more effective on long-running systems.

When available, this will be fully opt-in, scoped to your account, and governed by the same ownership guarantees that apply to your generated code: what you build is yours, and what you ingest stays private.

Connect Archon directly to your AI agents (like Claude Desktop) using the Model Context Protocol. This allows your agent to perform architectural analysis, validation, and materialization directly within your workspace.

⚠️ Path Verification

Ensure the paths to node and archon-mcp-client are correct for your system. You can find them by running which node and which archonspecs in your terminal.
